Agentic Adapter in Execution Time

MCP in the message path

How an IRIS interoperability production calls an MCP server while a message is in flight — which host does what, what crosses the production boundary, and where a language model does and does not sit.

The unit of work is a production. Five hosts, two of which carry adapters that reach outside. The example below enriches coded values in an HL7 message, but nothing in the shipped module knows what HL7 is — the same topology serves any message and any tool.

The story of one message

Seven steps. Every arrow below is a real hop, and every request is drawn with the reply that comes back to it — the catalogue, the chosen tool, the result. Four of the arrows in each external round trip are production messages, which means each one is recorded in the Message Viewer with its own body, its own timing and its own retry behaviour.

  1. The message arrives

    Sending system → HL7FileIn

    A standard business service. File, TCP with MLLP framing, FTP, REST — whatever the sending system speaks. Nothing about it is aware that an MCP server exists.

    Nothing changes at the edge. The inbound half of a live interface is untouched, so adding a tool call to an interface already in production does not mean re-testing how it receives.

  2. It is handed to your business process

    HL7FileIn → EnrichCodes

    An ordinary production message, delivered the ordinary way. Your process holds the logic: which values in this message matter, and what to do with an answer. For the common enrichment shape — find several values, improve each, forward the message — subclass Agentic.Adapter.EnrichmentProcess and write two methods. For anything else, any process, BPL or operation can drive the steps below directly.

    Separation of work. Knowledge of the message format lives here and nowhere else. The adapter never learns what HL7 is, which is exactly why the same adapter serves FHIR, X12, or a message class of your own without a line of change.

  3. Ask the server what it can do

    EnrichCodes → SnomedMCP → MCP server → back again

    A standard request to a business operation carrying Agentic.Adapter.MCP. The adapter holds the server address, the TLS configuration, the credential, the protocol version, the permitted tools, the result path and the error policy. It performs the MCP handshake and sends tools/list.

    What comes back is the catalogue: every tool the server offers, with its description and its input schema, each entry annotated with whether this interface is permitted to call it. That returns to your process as a ToolResponse.

    Configurability. The address, the certificate and the secret are settings on a production item, not constants in code. Repoint the item and every caller follows. And discovery replaces documentation — the tool name and result shape you need for the next steps come from the server itself, not from a vendor PDF.

  4. Decide which tool to use

    EnrichCodes → ToolSelector → Model provider → back again

    Only when the right tool cannot be known until the message arrives. The goal and the catalogue go to the model as text; a tool name and a reason come back as text. The model holds no credential for the tool server and has no network path to it — it names a tool, and AllowedTools is checked between its answer and the call.

    Selections are cached on whatever actually discriminates the case — the coding system, not the code. Measured over 50 messages: two model calls, forty-eight cache hits.

    Auditability of a judgement call. The one non-deterministic decision in the whole path is its own traced message. When a selection later looks wrong, the trace holds what the model was asked, what it answered, why, and whether the answer came from cache.

  5. Call the tool

    EnrichCodes → SnomedMCP → MCP server → back again

    The same operation as step 3, now with Action=call and the arguments. What comes back is the tool result — content blocks and structured content — reduced by ResultPath to the single value your process asked for, with the call duration attached.

    Retry, failover and alerting come for free. The adapter extends EnsLib.HTTP.OutboundAdapter, so a slow or unreachable tool server behaves like every other unreachable endpoint in the production: it retries, it fails over, it raises an alert, and the message is preserved rather than lost. Nobody writes that code.

  6. Apply the answer

    inside EnrichCodes

    Your second method. Write the value into the message, or reject the message, or route on it — the shipped error policy decides what happens when a value cannot be resolved: fail the message, pass it through unchanged, or substitute a default.

    The decision about data stays in your code. An unrecognised code is a data quality finding, not a broken interface, and which of those it is for your interface is a call only you can make.

  7. Forward it

    EnrichCodes → HL7FileOut → receiving system

    A standard business operation. The receiving system gets an improved message through the same channel it always used.

    The interface still ends where it always did. Everything between the two ends is production configuration and one class — which is what makes this reusable across use cases rather than a bespoke terminology feature.

Steps 3 and 4 usually disappear. Configure a tool name on the operation, or map a field in the message to one, and a message costs a single round trip — no catalogue fetch, no model, no cache. Discovery is for build time; the model is an escape hatch for when the right tool genuinely cannot be known in advance. Both are opt-in, and the path is deterministic without them.

The model never touches the tool server

The two adapters have no connection to each other. Everything the model learns about the tool server arrives as text in a prompt, and everything it decides comes back as text. It holds no credentials for the server, has no network path to it, and cannot invoke anything.

What ships, and what you write

Two levels, because an interface can reach out at two moments. Production level — invoke agents or MCP servers while exchanging data, on interface execution time. Transformation level — invoke them while transforming data or applying rules, on data execution time. An adapter has to hang off a business host, and a transformation is not one, which is why the second level is a function rather than an adapter.

The two methods are where the values live in my message and what to do with the answer. Everything else — the protocol, the catalog, tool selection, caching, error policy, the connections drawn above — is inherited. In the worked example that is 78 lines, and every line is about HL7.

If the shape does not fit

The base process assumes one common pattern: find several values, decide a tool for each, write the answers back. When your interface does something else — one call per message, routing on the answer, forwarding nothing — skip it. Any process, BPL or operation can send a tool request directly to the MCP item, and the adapter neither knows nor cares who called.
